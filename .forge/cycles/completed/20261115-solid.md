### Implementation Notes

**T1 measured (AC9-01), 2026-11-15.** Copy of the real profiles, databricks pinned 60 commits back and qdrant-skills
50 back, both updates held, release build of 2.5.1:

| Command | Time |
|---|---|
| `status` | 14.9 s |
| `review` | 14.3 s |

A git wrapper logged every call `status` made: **2 250 git processes, 2 227 of them `git cat-file blob`**, one per
side of every changed file, read for the risk flags. Everything else (rev-list, log, diff --raw, the Codex package's
clone and checkout, status --porcelain) adds up to under 0.5 s. So the fix is twofold: read the blobs in one
`git cat-file --batch` process (makes the first check fast, during `update`), and save the check (makes every later
command skip it).

## Learnings

- Measure before caching: the 14 s was 2 227 git processes, so batching fixed the first run and the cache the rest.
- A Refine key plan can collide with a mode (Discover's type-to-search); check the input model when assigning keys.
- Chain fmt, clippy, commit and push in one `&&` chain for RED commits too; a separate clippy call let a lint error through once.
